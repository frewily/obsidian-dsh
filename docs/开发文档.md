# DeepSeek Harness for Obsidian 开发文档

> 项目代号：obsidian-dsh
>
> 文档状态：设计阶段（v0.2，方向已调整：自绘 Claudian 式面板，非 iframe 完整 GUI）

## 1. 项目概述

### 1.1 背景与动机

[Claudian](https://github.com/xutiemin-arch/claudian) 证明了「把 AI CLI 嵌进 Obsidian vault」这条路可行：原生轻量聊天面板 + 引用笔记 + agent 以 vault 为工作目录干活。

DeepSeek Harness（以下简称 DSH）需要同等体验。社区已有 3 个同类插件（详见第 2 章），但实测存在交互断点。本项目的目标是**自研一个体验更好的 DSH 版 Claudian**：原生面板的轻量感，加上完整可靠的交互闭环。

### 1.2 目标

- Obsidian 桌面版内提供一个 Claudian 式原生聊天面板（跟随主题、轻量、随开随用）
- 对话后端复用完整 DSH：agent 以 vault 为工作目录，可读写 vault 文件、跑 bash、网络检索
- **交互闭环**：agent 的提问（`ask_user_question`）以 Obsidian 原生模态框呈现并可正常回答，工具调用可见、可停止
- 引用当前笔记 / 选中文本、`@` 提及笔记、会话历史
- 随 DSH CLI 升级自动获得后端新能力

### 1.3 非目标（明确不做）

| 事项 | 原因 |
| --- | --- |
| 移动端（iOS / Android）支持 | 移动端无 `child_process`，进程模型不成立；`manifest.json` 中 `isDesktopOnly: true` |
| 进程内打包 dsh 后端 | 依赖原生模块、包体巨大、与 Electron ABI 兼容风险高 |
| iframe 嵌入完整 Web GUI | 用户明确要 Claudian 式轻量原生体验；iframe 完整 GUI 可作为后续「高级模式」选项，不在 MVP |
| 修改 Claudian / 现有插件源码 | 独立自研，避免被他人代码与设计约束 |
| 接管 DSH 的模型/API Key 配置 | 复用 `~/.dsh` 现有配置（凭证、模型设置），插件不触碰密钥 |

## 2. 竞品调研与实测证据（2026-08-20）

### 2.1 社区现有插件

| 插件 | 作者 | 上架 | 技术路线 | 活跃度 |
| --- | --- | --- | --- | --- |
| [obsidian-deepseek-harness-native](https://github.com/wuruihi/obsidian-deepseek-harness-native) | wuruihi | ✅ 社区市场 | 自绘 UI + WebSocket 连本地 DSH Web 服务（127.0.0.1:3080） | 高（数小时内发版） |
| [DeepHarness](https://www.obsidianstats.com/plugins/deepharness) | 陈景帅 | ✅ 社区市场 | 自绘 UI + 每条消息 spawn `dsh --profile headless` | 高 |
| [obsidian-dsh](https://github.com/Tudo9710/obsidian-dsh) | Tudo9710 | GitHub | 自绘 UI + headless，JSONL 事件流 | 中 |

### 2.2 实测过程与发现的断点

在独立测试 vault 安装 native 与 DeepHarness 实测，会话文件（`~/.dsh/sessions/*/session.jsonl.zstd`）还原出以下事实：

| 测试项 | 结果 |
| --- | --- |
| 发任务（「用 bash 列出当前目录文件」） | ✅ agent 正常执行 |
| 写 vault 文件（「请在本地Vault中新建一个文件」） | ✅ agent 自行定位 vault 并用 write 创建文件 |
| **提问交互**（「问我今天想读哪本书，然后记下来」） | ❌ agent 构造好 `ask_user_question` 后**会话挂起**，无回答记录，用户弃用该会话 |
| **回复渲染** | ❌ 请求带 `reasoningEffort: max` 时，回复内容几乎全在 reasoning 增量里、text 输出为空，面板渲染不出可见回复（用户被迫重发同一问题） |
| DeepHarness 发送链路 | ⚠️ 只留下空会话（cwd 正确、权限预设正确，无消息） |

### 2.3 结论

- headless 路线（DeepHarness / Tudo9710）：`ask_user_question` 断点是**架构性死结**——headless 是单向任务，没有「提问 → 回答 → 继续」的交互协议
- native 路线：后端（连 `/api` + WebSocket）方向正确，但客户端 UI 未实现提问闭环与完整渲染
- 本项目采用 **native 的后端路线 + 自研完整客户端 UI**，把交互闭环做对

## 3. 技术背景与可行性依据

以下事实均已在 `@deepseek-ai/dsh@0.1.0-rc.7` 源码、CLI 实测与会话文件分析中核实。

### 3.1 DSH 侧事实

| 事实 | 依据 |
| --- | --- |
| `dsh web` 启动 Cordis 应用，托管前端静态资源与 `/api` 前缀的 HTTP RPC | `@deepseek-ai/dsh-web-app`、`dsh-host-apiproxy` |
| 浏览器事件通道为 WebSocket：`/api/events.mux`、`/api/events.host` | `dsh-client-connection` 源码 |
| 支持 `--port 0` 由系统分配端口；就绪后 stdout 打印 `dsh web: http://127.0.0.1:<端口>` | CLI 实测 |
| 默认绑定 `127.0.0.1`，`--trusted-host` 控制 `/api` 信任边界 | CLI 实测 |
| 用户数据根目录 `~/.dsh`，`DSH_HOME` 可覆盖 | `dsh-home-paths` 源码 |
| 会话按工作目录归档：`~/.dsh/sessions/--<cwd-path>--/session-<id>/session.jsonl.zstd` | 实测文件系统 |
| 官方客户端为浏览器包（`window.__ModuleLoader__` 加载），含连接、运行时、模块体系 | `dsh-client-connection` 等包 |
| 会话事件流类型（实测）：`session`、`permission/preset`、`user/message`、`assistant/message`、`assistant/chunk`（reasoning-delta / text-delta / block-start / block-end）、`tool-call-chunks`、`tool/call`、`tool/result`、`agent/inbox/spliced`、`turn/start`、`turn/end` 等 | 解压会话文件实测 |

### 3.2 Obsidian 侧事实

| 事实 | 依据 |
| --- | --- |
| 桌面版插件可 `require("child_process")` spawn 子进程 | obsidian-git、Shell commands、Claudian 等先例 |
| 自定义 `ItemView` 可承载任意 DOM（聊天面板、模态框） | 插件 API 标准能力 |
| `onunload()` 钩子可清理子进程 | 插件 API 标准能力 |
| 模态框 `Modal` 可承载结构化选项交互 | 插件 API 标准能力 |

### 3.3 方案选型（决策记录）

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 集成形态 | 自研独立插件 | 用户明确要自研；现有插件体验不佳 |
| 交互形态 | 自绘 Claudian 式原生面板 | 轻量、融入主题；iframe 完整 GUI 作为后续高级模式 |
| 后端 | **插件自管 `dsh web --port 0` 实例**（cwd = vault，复用 `~/.dsh`） | 拿到完整后端协议（会话/工具/权限/**提问**）；headless 路线有架构性提问断点 |
| 端口策略 | `--port 0` + 解析 stdout | 无冲突；不与用户手动启动的 3080 实例打架 |
| 前端实现 | 原生 DOM 或轻量框架（M1 定） | 插件体积小、加载快；参考社区插件模板 |
| 提问交互 | `ask_user_question` → Obsidian 原生 `Modal` 渲染选项并回传答案 | 闭环的关键，MVP 必须项 |
| DSH_HOME | 默认复用 `~/.dsh`，设置中提供独立 DSH_HOME 开关 | 与浏览器版共享配置 |
| dsh 本体 | 不打包，依赖系统安装（PATH 或手动指定路径） | 打包体积大；引导安装成本低 |

## 4. 总体架构

### 4.1 进程模型

```
┌─────────────────────────── Obsidian (Electron) ───────────────────────────┐
│                                                                           │
│  obsidian-dsh 插件（自绘聊天面板）                                         │
│  ┌──────────────┐   spawn    ┌────────────────────────────────────────┐  │
│  │ 进程管理器    │──────────▶│ dsh web --port 0 （独立 Node 进程）      │  │
│  │ (生命周期状态机)│  stdout   │  · HTTP RPC（/api）                    │  │
│  └──────┬───────┘◀───────────│  · WebSocket 事件通道                  │  │
│         │                    │  · 会话 / 工具 / 权限 / 提问 全协议      │  │
│  ┌──────▼───────┐            └──────────────────┬─────────────────────┘  │
│  │ 协议层        │  RPC + WS 事件                │                        │
│  │ (dshClient)  │                              │ cwd = vault 根目录      │
│  ├─ ChatView    │                              ▼                        │
│  ├─ AskModal    │                       Obsidian vault 目录             │
│  ├─ 会话历史     │                                                       │
│  └─ 笔记桥接     │                                                       │
└───────────────────────────────────────────────────────────────────────────┘
```

要点：

- 插件自管一个 `dsh web` 实例（`--port 0`），不依赖用户手动启动
- 插件通过 `/api` RPC + WebSocket 事件与后端通信，UI 全部自绘
- Agent 的 cwd 是 vault 根目录，可直接读写 vault（权限沿用 DSH 沙箱授权）

### 4.2 关键数据流（提问闭环，MVP 核心）

1. 用户发送任务 → 插件经 RPC 投递 → agent 开始工作
2. agent 调用 `ask_user_question` → 后端挂起该 turn，经事件通道通知客户端
3. 插件收到提问事件 → 弹出 Obsidian 原生 `Modal`（渲染问题、选项、多选）
4. 用户选择 → 插件经 RPC 回传答案 → 后端恢复 turn，agent 继续
5. 全流程渲染：reasoning 折叠块、text 流式输出、工具调用卡片、停止按钮

## 6. 模块设计

### 6.1 进程管理器（src/dshProcess.ts）

与 v0.1 设计一致：`spawn(dsh, ["web", "--port", "0", "--host", "127.0.0.1"], { cwd, env })`，正则 `^dsh web: (\S+)` 解析 URL，指数退避重启（60 秒内连续失败 5 次放弃），`onunload` 先 SIGTERM 后 SIGKILL。Windows 处理 `dsh.cmd`（`shell: true`）。

### 6.2 协议层（src/dshClient.ts）

对接 `/api` RPC 与 WebSocket 事件通道：

- 复用官方客户端包优先：调研 `@deepseek-ai/dsh-client-connection` / `dsh-cordis-client-runner` / `dsh-client-runtime` 是否可打包进 Obsidian（见 12 章风险 R1）
- 不可行则自实现轻量客户端：RPC 请求（`clientRequestSchema`、`RpcId`）+ 事件订阅（mux/host 双通道）
- 必须支持的事件：`user/message`、`assistant/chunk`（增量）、`tool-call-chunks`、`tool/call`、`tool/result`、提问事件、`turn/start`、`turn/end`、权限请求事件
- 断线重连（指数退避，对齐后端行为）

### 6.3 聊天面板（src/chatView.ts）

- 消息流：用户消息 / agent 消息（text + 可折叠 reasoning + 工具调用卡片）
- 输入框：Enter 发送、Shift+Enter 换行；`@` 模糊搜索提及笔记；「引用当前笔记/选中文本」按钮
- 工具栏：模型、推理强度、权限模式、停止（中断当前 turn）
- 渲染还原会话文件中的事件流结构（v0.1 实测：`assistant/chunk` 的 `reasoning-delta` / `text-delta` 增量）

### 6.4 提问模态框（src/askModal.ts）

`ask_user_question` 的核心闭环（本项目与现有插件的本质差异）：

- 收到提问事件 → 打开 Obsidian `Modal`：问题文本、选项卡片（label + description）、多选支持
- 提交 → RPC 回传答案 → 模态关闭，agent 继续
- 支持多个问题同时弹出（问题数组）

### 6.5 会话管理（src/sessionStore.ts）

- 新建 / 切换 / 历史会话，对齐 DSH 原生会话协议（RPC 能力）
- 会话按 cwd 归档于 `~/.dsh/sessions/`，插件读取展示历史标题与摘要
- Obsidian 重启后可恢复未归档会话

### 6.6 笔记桥接（src/noteBridge.ts）

- 「发送当前笔记」：将当前笔记内容/选中文本附带到任务
- 「结果回写」：把 agent 产出写入 vault（新笔记或追加），与 `新笔记.md` 实测场景对齐

### 6.7 设置（src/settings.ts）

```typescript
interface DshPluginSettings {
  dshBinaryPath: string;          // 留空 = PATH
  nodeBinPath: string;            // 留空 = 自动检测（Obsidian 内置 Electron 不是 node）
  workingDirectory: string;       // 留空 = vault 根
  useIsolatedDshHome: boolean;
  isolatedDshHomePath: string;
  autoStartOnLoad: boolean;
  viewTarget: "tab" | "sidebar";
  restartOnCrash: boolean;
  reasoningEffort: "off" | "high" | "max";  // 默认 high，避免实测的渲染空窗
}
```

## 7. 安全设计

| 风险 | 对策 |
| --- | --- |
| 本地服务被其他进程访问 | 显式 `--host 127.0.0.1`；不传 `--trusted-host` 放宽 `/api` 信任边界 |
| Agent 越权访问文件 | 沿用 DSH 沙箱授权弹窗（权限请求事件 → 插件渲染授权 UI），插件不绕过授权 |
| API Key 泄露 | 密钥只存 `~/.dsh`，插件不读取、不转发、不落盘 |
| 僵尸进程 | `onunload` 必杀；崩溃自动清理 |
| 误装恶意 dsh | 引导安装官方包 `@deepseek-ai/dsh`；支持手动指定路径并展示版本 |

## 8. 错误处理与边界情况

| 场景 | 处理 |
| --- | --- |
| Node.js 未安装 | 引导安装，给出官方下载链接 |
| dsh 未安装 / 不在 PATH | 引导 `npm install -g @deepseek-ai/dsh`，或手动指定二进制路径 |
| 启动超时（30 秒无 URL） | 终止，显示错误与 stdout 尾部日志 |
| 运行中崩溃 | 指数退避自动重启（可关闭）；连续崩溃放弃并提示 |
| WebSocket 断线 | 自动重连；后端存活时前端事件流自动恢复 |
| Obsidian 退出 | `onunload` 杀进程 |
| 多 vault | 每 vault 独立插件实例与设置；共享 `~/.dsh` 时提示会话串扰 |
| 提问超时（用户不回答） | 模态框可关闭，向 RPC 回传取消/超时，agent 收到后继续 |

## 12. 风险与开放问题

| 编号 | 风险 | 等级 | 说明与对策 |
| --- | --- | --- | --- |
| R1 | 官方客户端包无法直接打包进 Obsidian（ModuleLoader / UMD 形态） | **高** | M0 首先验证；不行则自实现轻量 RPC + WS 客户端（协议从 `dsh-host-apiproxy` / `dsh-client-connection` 源码与实测会话文件推导） |
| R2 | DSH 协议随 rc 版本变动 | 中 | 只依赖稳定契约（CLI 参数、stdout 行、核心事件类型）；升级前跑 M0 冒烟脚本 |
| R3 | 提问事件通道的具体形态（事件名/字段）尚未确认 | 中 | M0 用真实 agent 触发 `ask_user_question` 抓包确认 |
| R4 | Obsidian 未来收紧 child_process | 低 | 现有插件先例长期稳定；预案：提示用户手动启动服务 |
| R5 | 会话恢复 RPC 能力细节 | 低 | M1 阶段验证；不可行则插件自管会话索引（会话文件在 `~/.dsh/sessions/` 可读） |
| 开放问题 | 前端实现用原生 DOM 还是轻量框架（Svelte/Preact） | — | M1 开始时定；以插件体积与维护成本为准 |
