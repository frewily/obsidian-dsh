## 2. 0.2 协议调研与客户端路线结论 ✅

### 传输模型（源码核实）

- **上行**：HTTP POST `http://127.0.0.1:<port>/api/<method>`，body 为 JSON 信封；方法名即路径
- **下行**：两条 WebSocket 通道 `/api/events.mux`（会话事件）、`/api/events.host`（系统事件）；**下行 only**，客户端在 WS 上发消息会被 `close(1008, "downlink only")`
- 信任围栏：Host 非 loopback 且未在 `--trusted-host` → 403；无 `Origin` 头直接放行（Node 客户端天然安全）

### RPC 信封（四类）

```
client-request   { type, rpcId, method, payload }           客户端 → 服务器
server-response  { type, rpcId, result: {ok, value|error} } 服务器 → 客户端
server-request   { type, rpcId, method, payload }           服务器 → 客户端（WS 下行帧）
client-response  { type, rpcId, result }                    客户端 → 服务器（问答回传）
```

### 关键 RPC 方法（共 36 个）

会话：`session.create`（payload: `{cwd 或 workspaceId}`，返回 `sessionId`）、`session.prompt`（`{sessionId, mode: "queue"|"steer", content: [{type:"text", text}]}`）、`session.cancel`、`session.list`、`session.history`、`session.rename`、`session.search`、`session.fork`、`session.attachment`
其他：`host.describe`（就绪握手）、`credentials.describe/set/unset`、`llm.models/providers`、`settings.*`、`goal.*`、`subagent.*`、`workspace.*`、`skill.list`

### 提问闭环协议（核心验证目标）

```
agent 调用 ask_user_question
  → WS mux 下行帧 question/requested {sessionId, questions:[{id, question, header?, options?, multiSelect?}]}
  → 客户端 POST /api/respond，body = client-response 信封 {type:"client-response", rpcId: <帧的rpcId>, result:{ok:true, value:{sessionId, answer:{answers:[{id, selected:[], custom?}]}}}}
  → WS 下行帧 question/resolved {questionRpcId, outcome: "answered"|"cancelled"}
  → agent turn 恢复继续
```

### 客户端路线结论（消解设计文档 R1 风险）

- 官方 client 包（`dsh-client-connection` 等）为 `window.__ModuleLoader__.load({id, factory})` 的 UMD 形态，打包进 Obsidian 需 shim 且内嵌大量 UI 模块依赖，**不采用**
- 协议足够简单（4 类信封 + 方法名 = 路径 + WS 下行帧），**自实现轻量客户端**（原生 `fetch` + `WebSocket`，零依赖）为最终路线 ✅

## 4. 关键发现（回写设计文档）

### F1 凭证机制（重要：插件无需处理 API Key）

- `dsh` 启动时 `loadLayeredEnv` 自动加载 **`~/.dsh/.env`**（变量注入进程环境，优先级低于已继承变量）
- llm-deepseek provider 读 `DEEPSEEK_API_KEY`（默认），可用 `DEEPSEEK_BASE_URL` 覆盖端点
- **插件只要复用 `~/.dsh`，凭证自动可用**；独立 DSH_HOME 开关需要用户自行配置凭证
- 排障记录：`DASHSCOPE_API_KEY` 与 dsh 无关（曾误判为凭证来源）；`ps eww` 在 macOS 上环境输出有截断，不能作为环境判断依据

### F2 渲染事件结构（实测）

- `assistant/chunk`：`{type:"assistant/chunk", data:{turn, step, chunk:{type, ...}}}`
  - `chunk.type` 取值实测：`block-start`（`blockType: "reasoning"`）、`reasoning-delta`（`text` 增量）、`text-delta`（`text` 增量）、`finish`（`reason.kind: "error"` 时携带 `failure`，LLM 失败以此呈现）
- `assistant/message`：完整消息落定事件
- 会话初始化事件：`permission/preset`、`sandbox/mode`、`approval/policy`
- 会话按 cwd 归档：`~/.dsh/sessions/--<cwd路径(/)转-→--/session-<id>/session.jsonl.zstd`（zstd 压缩，JSONL 事件流，含 `session` 头 + 增量事件）

### F3 错误呈现

- LLM 失败（无凭证/401）以 `finish` + `reason.kind: "error"` chunk 呈现，**UI 必须展示该事件**（现成插件实测的"空回复"即为未处理此事件所致）

### F4 测试加固

- 测试实例以独立进程组 spawn（`detached`），所有退出路径（exit/SIGINT/SIGTERM/SIGHUP）按组清理（`kill(-pid)`），防孤儿进程
